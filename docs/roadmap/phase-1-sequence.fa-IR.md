# برنامه اجرایی ANA — فاز اول

## وضعیت مخزن

مخزن آغازین ANA در زمان شروع این کار فقط README کوتاه داشت. این شاخه، اسناد پایه را اضافه می‌کند؛ هنوز برنامه اجرایی، رابط کاربری یا اتصال واقعی مدل ساخته و آزمایش نشده است.

## ترتیب اجرا

### مرحله 1 — پایه مخزن و قراردادها
- [x] ایجاد شاخه مستقل برای فاز اول
- [x] ثبت معماری مغز، شخصیت و گفت‌وگوی فارسی
- [x] ثبت ممیزی منابع و محدودیت مجوزها
- [ ] انتخاب runtime اصلی پس از مقایسه عملی Tauri/Electron/Python
- [ ] افزودن اسکلت برنامه و تست CI

### مرحله 2 — چت فارسی با مغز Hybrid
- ساخت provider interface مستقل
- Gemini adapter
- OpenRouter adapter با فیلتر مدل‌های رایگان
- Ollama adapter اختیاری
- streaming، لغو پاسخ، timeout، retry و مدیریت rate limit
- تست خروجی فارسی و fallback
- هیچ API key در Git یا log ذخیره نشود

### مرحله 3 — شخصیت و حافظه
- بارگذاری پروفایل شخصیت از فایل نسخه‌دار
- mood state مستقل از شخصیت ثابت
- حافظه جلسه‌ای و بلندمدت
- ثبت، اصلاح، مرور و حذف حافظه توسط کاربر
- تست عدم ذخیره secret و عدم نسبت دادن محتوای وب به کاربر

### مرحله 4 — مکالمه صوتی
- ASR فارسی و VAD
- تشخیص پایان صحبت
- TTS با فهرست صدای قابل انتخاب
- barge-in: قطع فوری صدای دستیار هنگام شروع صحبت کاربر
- پخش صوت قابل لغو و جلوگیری از شنیدن صدای خود دستیار
- تست با نمونه‌های فارسی و نویز واقعی

### مرحله 5 — آواتار و احساس
- ابتدا renderer-neutral event bus
- Live2D renderer
- VRM renderer
- lip-sync/viseme و expression mapping
- اگر renderer خراب شد، چت و صدا همچنان کار کنند

## معیارهای پذیرش فاز اول

- [ ] تمام متن‌های پیش‌فرض و خطاها فارسی‌اند.
- [ ] مکالمه متنی فارسی با حداقل دو provider قابل انتخاب کار می‌کند.
- [ ] خطای provider به پاسخ خراب یا گم‌شدن متن کاربر منجر نمی‌شود.
- [ ] کاربر می‌تواند مدل و صدا را بدون تغییر شخصیت عوض کند.
- [ ] کاربر می‌تواند شخصیت را ویرایش یا به حالت پیش‌فرض برگرداند.
- [ ] حافظه بلندمدت قابل مشاهده، اصلاح و حذف است.
- [ ] دستیار با شروع صحبت کاربر، صدای خودش را قطع می‌کند.
- [ ] متادیتای احساس نامعتبر باعث شکست پاسخ نمی‌شود.
- [ ] برنامه بدون Live2D/VRM نیز چت و صدا را اجرا می‌کند.
- [ ] هیچ کنترل سیستم، دوربین یا ضبط پیوسته بدون اجازه فعال نیست.

## سیاست انتشار امن

هر مرحله در commit جداگانه انجام شود. قبل از هر تغییر ساختاری:
1. اجرای تست‌های موجود؛
2. ثبت commit/branch سالم؛
3. تغییر یک جزء؛
4. اجرای lint/typecheck/test/build مرتبط؛
5. ثبت نتیجه و امکان rollback.

تا وقتی runtime و ساختار فعلی مخزن تعیین نشده، وابستگی‌ها یا کد برنامه‌ای را به‌صورت حدسی اضافه نکن.
